### 4.2 직접 공격 — 무엇이 실제로 좁혀졌는가

이었다. 이번 재설계로 그 공격 **경로 자체**를 재분해했다:

| 하위 경로 | V2-C005 | V2-C006 (문면 재검토) |
|---|---|---|
| **다른 id를 새로 만들어(=미인가 id) 시도, 원하는 것만 커밋** | 통과(A-6이 사전선언 id를 자유선언하게 둠) | **차단** — `f`의 입력에 `countersign_commit_sha`가 들어가므로 인가 없이 통과하는 id를 계산할 수 없다(A-6). I-38로 명시 실측됨 |

**직접 공격 — `f`의 `countersign_commit_sha` 의존이 실제로 "인가 전 id 계산 불가"를 만드는가.**
문면상으로는 그렇다: `countersign_commit_sha`는 control branch의 커밋이고 executor는 그 브랜치에 쓰지
않는다는 것이 A-5·`EXECUTION_AUTHORITY §5`의 역할↔브랜치 대응에서 나온다. **그 전제를 직접 공격했다** —
실제 git/GitHub 권한으로 강제되는지 규약뿐인지.

```
$ git show .git/hooks/pre-push (symlink → scripts/hooks/pre-push, 저장소 정본)
  "그 외 브랜치(feat/* agent/* audit/* control/* …) — 통과."   ← control/* 도 명시적으로 통과
$ gh api repos/Siegfriex/ProjectFinal/branches/control%2Flanding-orchestrator/protection
  404 "Branch not protected"
$ gh api repos/Siegfriex/ProjectFinal/rulesets
  []
$ gh api repos/Siegfriex/ProjectFinal --jq '.permissions'
  {"admin": true, "maintain": true, "push": true, ...}
```

**결과: "executor는 control 브랜치를 못 쓴다"는 전제는 git/GitHub 수준에서 전혀 강제되지 않는다 — 순수
관례(제도적 역할분리)다.** pre-push 훅은 Pilot과 `research/landing-accessibility-main`만 실제로 막고,
`control/*`은 명시적으로 열어 둔다. 이 저장소의 모든 "역할"(executor/orchestrator/auditor)은 결국 동일한
git 자격증명으로 동작하는 에이전트 세션일 뿐이다.

**이것이 R-1 판단을 바꾸는가 — 아니다, 하지만 R-4의 범위를 넓힌다.** R-1(인가된 **하나의** id를 로컬에서
K회 실행) 자체는 이 발견과 무관하다 — control 브랜치 조작이 전혀 필요 없는, 순수 로컬 반복이기 때문이다.
control 브랜치 쓰기가 완벽히 막혀 있어도 R-1은 그대로 남는다. 반대로 이 발견이 실제로 넓히는 것은 **R-4**
(오케스트레이터 담합 시 인가 무제한)다 — R-4는 "담합"을 전제하지만, 실제로는 담합조차 필요 없다.
같은 자격증명을 쓰는 어떤 세션이든 control에 직접 써서 자기 인가를 스스로 발급할 수 있다. 이는 **이번
사이클에 새로 생긴 취약점이 아니다** — RC-6이 도입된 V2-C005부터 A-5가 이미 이 동일한 가정에 기대고
있었고, ssot V2-C005 §8 관찰 4가 이미 "명시 금지문은 원본에 없다"고 지적한 뒤 비차단으로 남긴 것과
같은 계열이다. 이번에 새로 한 것은 **문서상 결여를 넘어 git/GitHub 실측으로 강제수단 0을 확인**한 것뿐이다.
§6.2에서 신규 finding으로 등재한다 — 비차단.

### 4.3 R-1을 잔여로 수용하는가 — **수용한다. 동의한다.**

오케스트레이터 입장 — "원리적으로 저장소 내부 검사로 불가, 실제 완화는 운영 통제(통제된 러너)",
근거 — "다른 id 여러 개 만들어 고르기는 A-6이 닫았고 id 집합이 control이 인가한 `E`로 상한" — **동의한다.**

이유:

1. **원리적 불가능성은 참이다.** 커밋되지 않은 로컬 실행은 정의상 저장소에 어떤 흔적도 남기지 않는다.
   어떤 git 검사도 "일어나지 않은 커밋"을 조사할 수 없다 — 이것은 설계 결함이 아니라 "committed artifact만
   감사한다"는 이 감사 체계 전체의 근본 한계다. R-1을 저장소 검사로 닫으라는 요구는 성립할 수 없는 요구다.
2. **id 다양화 경로는 실제로 닫혔다.** `f`가 control 인가를 입력으로 요구하므로(§4.2 I-38), "여러 id를
   만들어 고르는" 것은 매 id마다 별도 control 인가가 필요하고, 그 인가 수는 A-8이 `E`로 상한한다. 이것은
   R-1과 **질적으로 다른** 경로이며 실제로 봉쇄됐다.
3. **정직하게 등재됐다.** R-1은 잔여표·닫힘 논거표·실패주입(I-41, 기대결과 `통과`) **세 곳**에 명시됐고,
   `:1334`의 과장된 단언은 철회됐다. 감사가 뚫은 구멍을 "닫혔다"고 위장하지 않고 경계를 정직하게 그은
   문서를 계속 blocking으로 묶어두는 것은 오히려 **정직한 등재를 처벌**하는 유인구조가 된다.
4. **분류가 위험도에 맞게 낮아졌다.** 원 finding은 P1/`V2_SSOT_FROZEN`-blocking(문서 동결 자체를 막음)이었으나
   R-1은 P2/`E001_V2`-blocking(실제 데이터 수집 착수만 막음)이다. R-1은 재수집이 실제로 실행되기 전에는
   행사될 수 없고, 실행 시점에는 (a) `03 Phase 5` 보고에 재수집 전후 값이 병기되고 (b) 두 독립 감사가 병행되며
   (c) `05 §6`의 executor self-approval 금지가 여전히 적용된다. 이는 R-1을 "닫는" 것이 아니라 **탐지·억제
   층으로 옮기는 것**이며, 그것이 정확히 오케스트레이터가 "운영 통제"라고 부른 것이다.
5. **오케스트레이터가 이미 R-1을 별도 blocking 항목으로 등재해 fail-closed를 유지했다.** 내가 원 finding을
   닫아도 `rc-6-r1-same-authorization-local-reexecution-unbounded`가 `open_blocking_total`에서 계속
   `E001_V2`를 막는다 — 즉 **아무것도 조용히 사라지지 않는다.** 이것이 "닫을 수 있는 것을 닫아라"는 지시와
   "잔여 위험은 잔여로 등재하면 된다"는 지시에 정확히 부합한다.
