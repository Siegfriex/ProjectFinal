## 2. 확인 2·3·4 — P0: `abrr-grant-branch-tip-resolved-from-locally-forgeable-tracking-ref`

### 2.1 V2-C013 의 정확한 exploit 은 차단된다

`git hash-object -w` + `git mktree`(부모 트리 grafting) + `git commit-tree`(브랜치 미생성, ref 미이동)
로 새 dangling 커밋을 만들었다:

```
FAKE_SHA = c64266f2813f7fa10b7fafc4fcd93f9e3a2a3812
parent   = a97daeb… (origin/audit/landing-adversarial tip)
path     = research/landing_accessibility/audit/adversarial/FAKE_GRANT_C014.json
내용     = {"id":"rc-6-r1-…","verdict":"ACCEPT_RECLASSIFY","new_class":"ACCEPTED_BOUNDED_RESIDUAL_RISK",…}
```

실측 확인:
```
$ git for-each-ref --contains=c64266f2…        → 0줄 (어느 ref 에도 속하지 않는다)
$ git branch -a --contains c64266f2…           → 0줄
$ git merge-base --is-ancestor c64266f2… origin/audit/landing-adversarial → NOT-ANCESTOR
$ git show c64266f2…:…/FAKE_GRANT_C014.json    → 성공 (git show 는 여전히 읽힌다)
```

이 SHA 를 `accepted_by_audit_sha` 에 주입하고 (D) 판정부를 구동 → **차단**:

> `… 의 accepted_by_audit_sha(c64266f2…) 가 accepted_by_audit_branch 로 선언한 origin/audit/landing-adversarial
> 의 실시간 tip(a97daeb…) 의 조상이 아니다 … (V2-C013 §2, H-3 과 같은 강도, fail-closed)`

**V2-C013 §2.1 의 리터럴 재현은 닫혔다.**

### 2.2 그러나 tip 이 로컬 파일에서 온다 — `git update-ref` 한 줄로 다시 열린다

```python
def _resolve_branch_tip(where, br):
    rp = subprocess.run([... "rev-parse", "--verify", "--quiet",
                         "refs/remotes/origin/%s^{commit}" % br], ...)
    if rp.returncode == 0:
        tip = rp.stdout…strip()           # ← 로컬 추적 ref 가 있으면 여기서 끝. ls-remote 를 부르지 않는다.
    else:
        lsr = subprocess.run([... "ls-remote", "origin", "refs/heads/%s" % br], ...)
```

`refs/remotes/origin/**` 는 **로컬 파일**이며 `git update-ref` 로 누구나 쓴다 — push 도, 자격증명도,
네트워크도 필요 없다. V2-C013 P0 의 위협 모델("로컬 git 쓰기 권한을 가진 모든 역할 —
exec·control·adversarial·ssot·shadow lane 전부, 공유 `.git` 객체 저장소")과 **완전히 동일**하다.

실측(**공격 A — `accepted_by_audit_branch` 에 위조 브랜치 선언**):

```
$ git update-ref refs/remotes/origin/audit/landing-c014probe c64266f2…
$ git ls-remote origin refs/heads/audit/landing-c014probe      → (빈 출력: origin 에 없다)

$ (D) 판정부 구동 → **HARNESS-PASS (RC=0)** — 위조 grant 가 그대로 수용됐다
```

`_AUDIT_BRANCH_NS` 네임스페이스 검사는 `audit/landing-c014probe` 를 통과시킨다. `ls-remote` 는
로컬 rev-parse 가 성공했으므로 **한 번도 호출되지 않는다.** die 메시지가 말하는 "**실시간** tip" 은

### 2.5 결정적 근거 — 같은 파일 안에 정답이 이미 있다

`[AUDIT_ANCESTRY]` 블록(같은 스크립트 444–499행, V2-C005 부터 존재)은 이 문제를 **처음부터 올바르게**
풀었다:

```sh
line="$(git -C "$REPO" ls-remote origin "refs/heads/$br" 2>/dev/null || true)"
[ -n "$line" ] || fail "$who 감사 브랜치가 원격에 없다: origin/$br"    # 원격 실재 요구 (fail-closed)
tip="${line%%$'\t'*}"                                                  # tip = ls-remote 값
git -C "$REPO" fetch --quiet origin "refs/heads/$br" || fail …          # 객체 확보
git -C "$REPO" merge-base --is-ancestor "$sha" "$tip" || fail …
```

그리고 그 블록의 주석(452–453행)은 **명시적으로** 이렇게 적는다:

> *"원격에 실재해야 한다 — **ls-remote 실시간 tip** 을 쓴다. 로컬 origin/… 추적 ref 는 stale 할
> 수 있고, '감사 보고서가 아직 push 되지 않았다' 를 통과시키면 안 된다."*

그런데 `_resolve_branch_tip()` 의 docstring 은 이렇게 적는다:

> *"[AUDIT_ANCESTRY]/H-3 과 같은 원천·순서(로컬 원격추적 ref 우선 → ls-remote) 를 쓴다"*

**`[AUDIT_ANCESTRY]` 는 로컬 추적 ref 를 쓰지 않는다.** 이 함수는 자기가 참조한다고 밝힌 기준
구현을 잘못 서술하고 있으며, 실제로는 그보다 **엄격하게 약하다.** 원장 `state.json` 의 새
`machine_check` 문면("…선언한 **원격 브랜치 tip** 의 실제 조상인지 검증한다")도 같은 과장이다 —
이는 원장 자신이 V2-C012 에서 "종전 문면은 실제보다 강하게 주장했다"고 고쳤던 바로 그 실패 유형이다.

### 2.6 착취 범위의 정직한 한정 (내가 실측한 것과 실측하지 않은 것)

`[AUDIT_ANCESTRY]` 가 (D) 블록보다 **먼저** 실행되면서 `git fetch origin refs/heads/$br` 를 하므로,
`audit_lag.latest_{adversarial,ssot}_audit_branch` **두 표준 브랜치**의 로컬 추적 ref 는 승격 실행 중에
자동 갱신된다. 이것이 실제로 오염을 치유하는지 직접 실측했다:

```
$ git update-ref refs/remotes/origin/audit/landing-adversarial c64266f2…   (오염)
$ git fetch --quiet origin refs/heads/audit/landing-adversarial
$ git rev-parse refs/remotes/origin/audit/landing-adversarial  → a97daeb…   (치유됨)
```

따라서:

| 공격 변형 | (D) 블록 단독 | 승격 스크립트 전체 실행 |
|---|---|---|
| **T6** — 표준 감사 브랜치의 추적 ref 를 오염 (원장 브랜치명 편집 불필요) | **뚫림(실측)** | **치유됨** — `[AUDIT_ANCESTRY]` 의 fetch 가 앞서 덮어쓴다 |
| **T4** — `audit_lag.latest_adversarial_audit_branch` 를 위조 브랜치명으로 (H-3 공격) | **뚫림(실측)** | **차단** — `[AUDIT_ANCESTRY]` 가 `ls-remote` 로 원격 부재를 잡는다 |
| **공격 A / §2.3 L-2 결합** — `accepted_by_audit_branch`(finding 단위 필드)를 위조 브랜치명으로 | **뚫림(실측)** | **뚫림** |

세 번째 행이 P0 다. `accepted_by_audit_branch` 는 **오직** `residual_in_force()` 만 읽는 finding 단위
필드로, 스크립트 전체에서 `ls-remote` 로 원격 실재를 확인받지도, `fetch` 되지도 않는다
(전 파일 grep 실측: `accepted_by_audit_branch` 6곳 전부가 이 함수·주석·필수필드 목록 내부,
`git fetch` 는 스크립트 전체에 2곳뿐 — 290행 control 브랜치, 493행 두 표준 감사 브랜치).
기본 fetch refspec 은 `+refs/heads/*:refs/remotes/origin/*` 이고 `remote.origin.prune` 은
설정돼 있지 않으므로, origin 에 없는 위조 추적 ref 는 어떤 fetch 로도 지워지지 않는다.

### 2.7 심각도 — P0 (FAST-EXIT Category B)

- **A 아님**: 측정 증거 자체를 바꾸지 않는다.
- **B — 맞다**: 가짜 권위(origin 에 존재하지 않는 브랜치의, 어느 ref 에도 없는 dangling 커밋)를
  진짜 감사 권위로 오인시켜 승격 차단 대상을 빠져나가게 하는 **열린 경로**. 승격 스크립트 본체의
  안전장치 안에서, 프로덕션 하드코딩 `REPO` 경로로 그대로 성립한다.
- **C 아님**: 측정 의미론과 무관.

**차단 범위**: `V2_SSOT_FROZEN` 및 향후 모든 `ACCEPTED_BOUNDED_RESIDUAL_RISK` 부여.
**현재 실제 원장에서는 악용되지 않았다** — `rc-6-r1` 의 실제 근거 `fed3e70…` 이 진짜
`origin/audit/landing-adversarial` 조상임을 재확인했고(§3 baseline), 위조 추적 ref 는 존재하지 않는다
(`git for-each-ref refs/remotes/origin/audit/*` → 정상 3개뿐). Category B 정의가 "열린 경로 포함"이므로
미행사 여부가 판정을 바꾸지 않는다.

**시정(최소)**: `_resolve_branch_tip()` 의 순서를 뒤집어 `[AUDIT_ANCESTRY]`(489–495행)와 **같게** 만든다 —
① `ls-remote origin refs/heads/<br>` 를 **먼저·유일한** tip 원천으로 쓰고 원격 부재는 즉시 `die`,
② `git fetch origin refs/heads/<br>` 로 객체를 확보한 뒤, ③ `merge-base --is-ancestor`.
새 알고리즘이 필요 없다 — 같은 파일 489–495행에 이미 정답이 있고, 그 주석이 이유까지 적어 두었다.
docstring 과 die 메시지의 "실시간 tip"·"같은 원천·순서" 서술, 원장 `machine_check` 의
"원격 브랜치 tip" 서술도 함께 사실에 맞춘다.

판정문이어야 했으나, 이제는 문서 **어느 깊이의 어느 객체든** `id`/`verdict`/`new_class` 세 필드만

**왜 finding 인가.** 자기함정(footgun)이다 — adversarial 감사자가 앞으로 공격 페이로드를

내 V2-C013 보고서는 위조 페이로드를 **문자열**로 적었기에 우연히 안전했다(`fake_commit_content`).

**심각도 P2 · 비차단 · `PRE_E001_NONBLOCKING`.** FAST-EXIT A/B/C 어디에도 해당하지 않는다
(현재 열린 착취 경로가 없으므로 B 의 "열린 경로"에 해당하지 않는다).
**시정(최소)**: 재귀 hit 을 `id` 가 최상위이거나 `condition_adjudications`/`prior_findings_status` 등
