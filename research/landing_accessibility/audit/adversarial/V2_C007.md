## 3. 시정이 ssot 지적을 정확히 닫는가

ssot V2-C006(`444de06`)의 blocking finding `execution-authority-baseline-ssot-audit-row-not-updated`는
§5의 ssot 행이 `V2-C003 @ 43fab0ac`로 세 사이클째(V2-C004→V2-C005→V2-C006) 정체돼 있고, 같은 문서
§6 감사이력은 이미 최신 사실(V2-C005)을 담고 있어 **문서 내부 모순**이라고 지적했다. 처방 문구는
그 시점의 최신 tip인 `V2-C005 @ 39e485c8`을 가리키라는 것이었다.

실제 시정은 `V2-C006 @ 444de06`을 가리킨다 — 처방의 문자 그대로가 아니라 **한 사이클 더 최신
값**이다. 이것이 정확한지 직접 확인했다:

```
git rev-parse origin/audit/landing-ssot  →  444de0607993e766fd2686b377f42a6d9b7f7dae
```

`444de06`은 **바로 그 지적을 담은 ssot V2-C006 보고서 자신의 커밋**이며, 지시 시점(ssot 감사
작성 시)에는 아직 존재하지 않았던 값이다(자기 자신을 인용할 수 없으므로 처방이 한 스텝 뒤처진
값을 쓴 것은 불가피했다). exec는 문자 그대로가 아니라 **"§5 ssot 행 = `audit/landing-ssot`의
현재 tip"이라는 원칙**을 따라 실행 시점의 실제 최신값을 넣었고, 이는 `git rev-parse`로 직접
검증한 현재 tip과 정확히 일치한다. **처방보다 더 정확한 시정이며, 지적한 근본 원인(문서 내부
모순)을 정확히 닫는다.** 부적절하다고 볼 근거 없음.

`INSTALL_MANIFEST.json`의 `sha256` 갱신도 확인했다 — TARGET 트리의 실제
`EXECUTION_AUTHORITY.md`를 `sha256sum`으로 직접 재계산한 값(`9889ebf8...ba37a`, 14016
bytes)이 매니페스트에 기재된 값과 바이트 단위로 일치한다.

## 5. 내 V2-C006 PASS(blocking 0)가 흔들리는가

**흔들리지 않는다.** 근거:

1. **표면이 겹치지 않는다.** 내 V2-C006 PASS는 재수집 RC-6/A-6~A-8, 배너 회귀 테스트,
   `install-manifest` 커버리지, debt 재계산 이중소스를 대상으로 했다. 이번 diff는 그 중 어느
   코드·데이터·정책 파일도 건드리지 않았다 — §2에서 확인한 대로 변경은 두 문서의 "기준선
   포인터" 텍스트뿐이다.
2. **`open_blocking_total` 계산 메커니즘 자체가 무변경.** `promote_landing_main.sh`의
   `DEBT_RECOMPUTE` 로직, `control/state.json`, `debt_ledger`는 이 diff에 등장하지 않는다.
   내가 V2-C006에서 독립 재현한 `14 = 담당 밖 12 + ssot 관련 2`라는 계산식의 입력 파일이
   하나도 바뀌지 않았으므로 그 재현 결과는 여전히 유효하다.
3. **이번 diff가 닫는 것은 ssot 쪽 blocking 1건(§3)이며 내 몫이 아니다.** ssot가 자신의
   V2-C007 감사에서 이 시정을 확인하고 `open_blocking_total`을 갱신하는 것이 정상 절차다
   (오케스트레이터 reconciliation 대상). 이 감사는 diff 자체가 올바르고 부작용이 없음만
   확인하며, ssot의 판정을 대신하지 않는다.
4. **Pilot·root CLAUDE.md·state parquet·C013·evidence·control 불변조건**은 §2에서 diff 0으로
   직접 확인했다 — V2-C006에서 확인한 불변조건 목록과 동일하게 전부 유지된다.
