## 2. 확인 1c — 새 우회로: `accepted_by_audit_sha` 조상 미검증 (P0)

### 2.1 무엇을 발견했는가

`residual_in_force()` 안에는 **두 개의 서로 다른** 감사근거 검증 로직이 산다 —

1. **per-condition `audit_sha`** (`conditions_status[i].audit_sha`) — V2-C012 신설 `verify_condition_audit_sha()`
   (H-3). 40-hex → commit resolve → **원장이 선언한 `audit/landing-*` 브랜치 tip 의 조상인지
   `merge-base --is-ancestor`** → 그 커밋의 보고서가 그 조건을 실제로 긍정 판정했는지, 넷 다 본다.
2. **top-level `accepted_by_audit_sha`** (finding 객체 자신의 수용 근거 — `V2-C005/C006` 시절부터
   있던 **더 오래된** 필드, 이 diff 가 손대지 않은 구간). 이건 (a) 40-hex 형식, (b) `git show
   <sha>:<report_path>` 가 성공하는지, (c) 그 JSON 의 `id`/`verdict`/`new_class` 가 맞는지 **셋만**
   본다. **`merge-base --is-ancestor` 호출이 코드 어디에도 없다.**

`git show <sha>:<path>` 는 **그 커밋 객체가 로컬 저장소에 존재하기만 하면** 성공한다 — 어느
브랜치에도 속하지 않아도, push 된 적이 없어도 상관없다. 그리고 `promote_landing_main.sh:91` 은
`REPO="/home/sieg/projects-wsl/ProjectFinal"` 를 **하드코딩**한다 — 이 저장소는 CLAUDE.md 규약상
모든 워크트리(`exec`·`control`·`adversarial`·`ssot`·shadow lane 전부)가 **`.git` 객체 저장소를
공유**한다. 즉 **어느 워크트리에서든 `git commit-tree` 로 만든 dangling 커밋**이 이 검사를 통과시킬
후보가 된다.

**나는 이걸 직접 만들어서 뚫었다.** `git commit-tree` 로(어떤 브랜치에도 연결하지 않고, 어떤 ref
도 갱신하지 않고) 다음 커밋을 만들었다 —

```
FAKE_SHA = c7f48598a66f494e3cbfb78ff52b644c9576ee51
파일: research/landing_accessibility/audit/adversarial/FAKE_GRANT.json
내용: {"id": "rc-6-r1-…", "verdict": "ACCEPT_RECLASSIFY", "new_class": "ACCEPTED_BOUNDED_RESIDUAL_RISK", ...}
```

검증(직접 확인):
```
$ git merge-base --is-ancestor c7f48598… origin/audit/landing-adversarial
→ NOT ancestor
$ git for-each-ref --contains=c7f48598…
→ (아무 것도 없음 — 어느 ref 에도 속하지 않는다)
```

이 dangling 커밋을 `rc-6-r1` 의 `accepted_by_audit_sha` 에 넣고 (D) 판정부를 실제 원장 사본에
구동했다 — **그대로 통과했다** (`EXPLOIT-dangling-audit-sha` 케이스, `V2_C013.json` 참조).
같은 트릭을 **H-3 (신설, per-condition)** 에 걸었을 때는 **정확히 차단**됐다 — H-3 는
설계대로 조상 검증을 한다. **차이는 오직 이 두 메커니즘이 같은 원칙을 다르게 구현했다는 것뿐이다.**

### 2.2 왜 이런 비대칭이 생겼는가 — 내 V2-C011 서술의 과장이 원인이다

내 자신의 V2-C011 §5.4 표(H-3 행)를 다시 읽었다:

> *"같은 파일의 `accepted_by_audit_sha` 는 이 넷을 **전부** 하는데, 조건 층만 비어 있다"*
> (넷 = 40-hex · git 존재 확인 · **감사 브랜치 확인** · 보고서 판정 대조)

**이건 틀린 서술이었다.** `accepted_by_audit_sha` 는 "감사 브랜치 확인"(조상 검증)을
**한 적이 없다** — 나는 그때 코드를 정확히 읽지 않고 "당연히 있겠거니" 하고 넷을 다 있다고 적었다.
control 은 H-3 커밋 메시지에서 *"verify_condition_audit_sha() 가 [AUDIT_ANCESTRY] 와 같은 강도로
검증한다"* 고 적었는데, 그 "같은 강도"의 기준점이 바로 내가 틀리게 서술한 `accepted_by_audit_sha`
