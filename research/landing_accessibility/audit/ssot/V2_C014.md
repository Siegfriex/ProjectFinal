## 2. 검증강도 대조 — "무늬만 검증"인가

adversarial 이 지적한 P0 의 본질은 **top-level grant-evidence 층이 ancestry 검증을 전혀
호출하지 않았다**는 것이다. control 은 "H-3 이 이미 구현한 것을 재사용했다"고 주장한다.
이 주장을 코드로 대조했다.

### 2.1 `_resolve_branch_tip()` — 실제 재사용인가 : **참**

`17389a2` 의 `audit_branch_tips()` 안에 인라인돼 있던 tip 해석 로직이 그대로 함수로 추출됐다.
diff 대조 결과 **동작 순서·조건·실패처리가 모두 동일**하다.

| 항목 | 종전 (인라인) | 신규 (`_resolve_branch_tip`) |
|---|---|---|
| 1차 원천 | `git rev-parse --verify --quiet refs/remotes/origin/<br>^{commit}` | 동일 |
| 2차 원천 | 실패 시 `git ls-remote origin refs/heads/<br>` | 동일 |
| 형식 강제 | `HEX40.match(tip or "")` 실패 시 `die` | 동일 |
| 실패 방향 | fail-closed | 동일 |

차이는 `die()` 메시지에 호출지점(`where`)이 붙은 것뿐이다. `audit_branch_tips()` 는 이제
같은 함수를 호출하므로 **두 층이 문자 그대로 하나의 구현을 공유**한다. 정규식도
`startswith("audit/landing-")` → `_AUDIT_BRANCH_NS = ^audit/landing-[A-Za-z0-9._/-]+$` 로
H-3 쪽과 동일한 상수로 통일됐다 (종전 top-level 은 접두 검사라 `audit/landing-` 뒤에
임의 문자가 와도 통과했다 — 이것도 함께 좁혀졌다).

`declared_branch_tip()` 은 캐시만 분리한 얇은 래퍼다. 캐시 분리는 정당하다 —
`audit_branch_tips()` 의 `if _AUDIT_TIPS: return _AUDIT_TIPS` 단락평가와 같은 dict 를
공유하면 표준 2브랜치가 아닌 값이 첫 진입 시 캐시를 채워 두 표준 브랜치 해석을
건너뛰게 만든다. control 의 주석 설명이 정확하다.

**실측.** `origin/audit/landing-adversarial` 의 로컬 원격추적 ref 와 `ls-remote` 결과가
현재 완전히 일치한다(`a97daeb…`). `origin/audit/landing-ssot` 도 일치(`bc1a612…`).
정당한 grant `fed3e70…` 은 `git merge-base --is-ancestor fed3e70 origin/audit/landing-adversarial`
→ **YES**. 즉 시정 후에도 진짜 grant 는 통과한다(회귀 없음).

### 2.2 `abrr_grant_hits()` — 어휘를 갈아끼운 변명인가 : **아니다 (실측으로 확인)**

control 은 `adjudication_hits()` 를 그대로 호출하지 않은 이유로
"그 함수의 긍정어휘(`SATISFIED`/`MET`/…)는 수용 등급 부여 어휘와 달라 항상 0 hit 이 되어
사실상 새 `die` 사유를 만드는 것과 같다"고 적었다. **이 주장을 검증했다** — `a10663e` 의
스크립트에서 두 함수를 그대로 추출해 실제 grant 문서
(`fed3e70:…/audit/adversarial/V2_C008_focused.json`)에 태웠다.

```
abrr_grant_hits(adj, "rc-6-r1-…", ABRR)
  -> ['id=rc-6-r1-… verdict=ACCEPT_RECLASSIFY new_class=ACCEPTED_BOUNDED_RESIDUAL_RISK']
adjudication_hits(adj, "rc-6-r1-…")
  -> []                                  ← control 의 주장이 사실임
```

즉 `adjudication_hits()` 재사용은 실제로 불가능했다. 신설은 정당하다.

`abrr_grant_hits()` 가 `adjudication_hits()` 와 **같은 설계**인지도 대조했다 —
재귀 walk(dict/list), 부정어휘 우선, id 매칭 후 판정. 일치한다. 판정 강도는
종전 top-level 등가비교 대비 **한 축에서 더 강하다**: `new_class` 를 정규화 후 **완전일치**로
보고(부분일치 아님), `verdict` 는 긍정어휘 포함 + 부정어휘 부재를 **함께** 요구한다.

**부정 프로브 4종 실측 (전부 기대대로).**

| 프로브 | 결과 |
|---|---|
| `new_class` 를 다른 값으로 | `[]` (차단) |
| id 불일치 | `[]` (차단) |
| `verdict="ACCEPT_RECLASSIFY_REJECTED"` (긍정·부정 동시) | `[]` (부정 우선 — 차단) |
| 중첩 문서에 `REJECT` 자리와 `ACCEPT_RECLASSIFY` 자리 공존 | **hit** (→ S7) |

### S3 · `control-cycle-artifact-claims-audit-branch-tips-byte-unchanged-but-it-was-refactored` — P2 / non-blocking

`V2_C014_orchestrator.json` `what_i_did.diff_scope` 가
"`audit_branch_tips()`/`adjudication_hits()`/`verify_condition_audit_sha()`/`_ABRR_CANON`/
`gate_declared_achieved()`/`tally()` 등 H-1~H-5 코드는 **바이트 무변경**" 이라고 적고,

치환되고 정규식 리터럴이 상수로 바뀌었다 — **바이트 무변경이 아니다**.

같은 파일의 `measured_not_assumed.diff_scope_verification` 은 무변경 집합을
"`_ABRR_CANON`·`gate_declared_achieved`·`verify_condition_audit_sha`·`adjudication_hits`·`tally` 등"
으로 적어 `audit_branch_tips()` 를 **제외**한다 — 두 절이 서로 모순된다.

기능 영향은 없다. §2.1 에서 리팩터가 동작 등가임을 확인했다. 그러나 이 사이클의 주제가
"자기서술 과대주장의 정정" 이라는 점에서 같은 종류의 부정확이 같은 커밋 안에 남은 것은
기록해 둘 가치가 있다.
부수: 커밋 메시지는 회귀 케이스를 "기존 26건", `state.json` `machine_check_history` 는
"기존 28건" 으로 적는다 — `attack_matrix.case_count=28` 중 신규 2건을 뺀 26 이 정확하므로
`state.json` 쪽 문면이 느슨하다.
